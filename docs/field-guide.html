Your question 1

CI: a checklist that every push must pass

Yes. CI is a fixed set of automatic checks. On every push, GitHub starts a fresh, empty machine, downloads the repo and runs the same checks you run with make check. If any check fails, the run turns red and nothing gets published. A clean machine matters: leftovers on your desktop can't hide a problem.

Restaurant version: the inspector cooks a sample of the new recipe in an empty test kitchen, then ticks a checklist. One unticked box and the batch never leaves.

Your question 2

Ansible: the manual a robot follows

Yes, that's the core of it. The roles describe how a finished server should look. Ansible connects over SSH and makes the server match: on a fresh AlmaLinux it builds everything; on an existing one it changes only what differs. A new server or a reinstall becomes one command instead of an evening of remembering.

SettingThe manual saysLab VM today (verified)1st run2nd run

This is idempotency: the second run finds nothing to fix and reports changed=0. That number is how we prove a role is correct.

What else Ansible gives this project

  • Drift detection. --check --diff shows where the server no longer matches the manual, without changing anything. Your hand-made SSH change from step 0.3 is exactly the kind of drift it catches.
  • Every change is reviewed. Server changes are Git commits you can read, discuss and revert.
  • Safe testing. The same roles run on the lab VM first, so mistakes cost a reset, not an outage.
  • Documentation that can't go stale. The roles are the description of the server, and they are what actually runs.
  • Restarts only when needed. Handlers restart Caddy or sshd only if their config really changed.
  • Secrets handled properly. Passwords and keys live in an encrypted vault file, never in plain text.
  • Scales to more servers. The monitoring node in step 3.1 reuses base, users_ssh and firewall as they are.
  • A real skill. Ansible is standard in RHEL shops; Red Hat sells it as Ansible Automation Platform.

The research

What helps beginners learn complex technical topics

Feeling lost on a first pass through Ansible, CI and Linux security at once is normal. The research says what works better than rereading long explanations.

TechniqueWhat the research foundStrengthHow we use it here
Practice testingRecalling an answer from memory beats rereading it. Rated "high utility" in a review of 10 techniques.strongEach session starts with 3 short questions from the recall queue; the answer follows each one, and a missed one comes back next time.
Spaced practiceComing back to a topic over days beats one long session. Also "high utility".strongOld concepts come back in later quizzes; the learning log becomes flashcards.
Worked examples, then fadingBeginners learn more from studying complete solutions than from solving alone; the benefit fades as skill grows, so help should shrink step by step.strongI write the first roles with comments on every task; later you predict, then edit, then write one task yourself.
Predict + explainExplaining why, while predicting what code will do, beats predicting alone or just watching. Meta-analysis effect around g = 0.55.mediumBefore each dry run I explain the mechanism and offer 2–3 outcomes; you pick one. The "why" comes after the run.
Explain first, then askBeginners on material with many moving parts learn more from an explanation or worked example first. A question about something not yet shown is a blind guess, and blind guesses teach little.strongI never open with a question on a new topic. Every question is about something you have just seen.
Watching is not learningStudents who only watched a demonstration did barely better later than students who never saw it. Those who first picked an outcome from a list did clearly better, although only 26% picked right.mediumYou still commit to an answer before a run. Being wrong is expected about one time in five.
The answer always followsWhen the right answer is given afterwards, a question teaches whether your first answer was right or wrong. A hard question with no answer after it teaches almost nothing.mediumAfter every question I give the answer and one sentence of reason. No question is left hanging.
Words + meaningful diagramsPeople learn more from words with relevant pictures than from words alone; decorative pictures don't help.mediumEvery new mechanism gets one small diagram next to the text, like the ones on this page.
Rereading, highlightingAmong the least effective techniques, though the most popular.weakDon't reread my long messages; answer the recall questions instead.

The first three rows come from peer-reviewed reviews. The diagram findings come from Richard Mayer's work as summarised by secondary sources, so the exact numbers are low-confidence. Effects are real but moderate, and the active techniques cost more time per topic.

How we'll work through every piece from now on

  1. Place it on the map.I say which box or arrow above this piece changes. Once a topic is familiar, you say it.
  2. Worked example.I write the code with a short comment on every task: what it does and why.
  3. Show, then check.After each explained piece, one short question about one thing you have just seen.
  4. Predict by choosing.Before the dry run I show the diff and the server's current state, explain the mechanism, and offer 2–3 outcomes. You pick one and say how sure you are.
  5. Run and compare.We read the --check --diff output against your pick, then one question on the difference.
  6. Explain it back.One or two sentences in your own words. At first I give you the frame: "X makes … so that …; without it …".
  7. Recall next session.Three questions from the recall queue before we start; the answer follows each.
  8. Fade the help.On familiar topics the question comes before the explanation; later you write one small task yourself and I review it.

How a check question is built

Changed on 2026-11-27, after the questions turned out too hard too often. Every question now comes after an explanation, asks about one idea, and can be answered from what is on screen. The forms go from easy to hard, and we climb only after success.

StepFormExampleWhen
1Pick one of 2–3The task has notify: restart sshd. Does sshd restart A) after that task on every run, B) once at the end and only if the task reported changed, C) at the end of every play?Right after an explanation
2Fill the gapOur file is named 01-hardening.conf because sshd reads drop-ins in … order and the … value wins.Right after an explanation; recall
3Trace or predict one thingfirewall-cmd --list-services prints ssh; the diff adds http and https. What does it print after the run?Before a run; recall
4Explain one lineIn one sentence, what is AllowUsers kai deploy for?End of a step; recall
5What ifThe deploy dies after the copy but before the symlink switch. What does a visitor see?Milestones
6Teach backA maintainer asks why we use releases plus a symlink instead of copying into the live folder. Answer from the map.Milestones, on topics that passed steps 1–4
  • Two misses in a row: the next question is one step easier. Three or four right on the first try: one step harder. About four of five right is the target.
  • Wrong answer: I say what is right in it, give one hint, you try once more, then I give the answer and you say it back in your words.
  • "I don't know" is a fine answer. I then offer options or point to where the answer is visible; if that fails, my explanation was too big and I explain a smaller piece.
  • "Makes sense" does not count as an answer, because feeling that you understood is the least reliable signal there is.

The six steps are a synthesis of several studies, not one tested method, and no study covers infrastructure code. Details, numbers and what was verified: docs/research/2026-11-practices-review.md. Questions waiting for the next sessions: docs/recall-queue.md.

For future projects

  • Draw the big map first: boxes, labelled arrows, one comparison everyone understands. Update it when the system changes.
  • Keep a learning log (you already have one) and turn each entry into a question you can answer from memory.
  • Always build a lab first. Break things there on purpose (a wrong firewall rule, a bad SSH config) and recover through the console.
  • Write one short post per big concept. Explaining to strangers is the strongest test of understanding.
